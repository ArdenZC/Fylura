# Files workbench

Tracking: [#553](https://github.com/ArdenZC/Fylura/issues/553). Native acceptance: [#487](https://github.com/ArdenZC/Fylura/issues/487).

`FileWorkbenchModel` owns disposable pane/controller instances and each tab's count (1–4), layout, active pane and split weights. `panes` may contain dormant panes beyond `paneCount`: changing the count preserves them; explicit close disposes only that pane. Reordering moves the existing pane instance. No new Browse or file operation engine is introduced.

`WorkbenchLayout` owns CSS grid and pointer/keyboard separator interaction. Three panes use columns; four default to 2×2. Each visible column needs 500px, and the grid needs 640px height; below that the active pane fills the area and buttons/F6 switch panes. Hidden panes keep their DOM/pages/selection, stop observation and close Quick Preview. Explicit refresh, navigation and post-mutation invalidation continue to replace stale pages on the existing owners. Backend page, entry/path reference and ticket limits remain unchanged. Browse session metadata has 96 bounded slots for 32 pane roots plus history, tree and admission cleanup overlap; Runtime and BrowseService share the same allowance. Process-wide 200k entry / 32,768 path budgets still prevent per-pane multiplication. The existing controller releases only re-admissible inactive history before new Browse admissions; history intent and presentation remain intact, and Back/Forward obtains fresh refs. Opaque history remains retained.

Persistence keeps the existing `zen-canvas:file-library-workbench:v1` key to find old data, writes format version 2 and accepts versions 1/2. Version 1 `dual` becomes `paneCount`; its hidden second pane is retained. Parsing remains bounded and rejects unknown fields/invalid split weights. Only paths, validated restore metadata and UI layout persist; refs, tickets, previews and mutations never do. Restore applies saved Browse query/view presentation after fresh backend admission. Pane visibility and root search handoff stay inactive until restore completes, avoiding cancellation of the root restore by intermediate tab construction.

The toolbar selects a destination pane explicitly. Drag capture records all visible destination identities and paths; drop and asynchronous ticket handoff revalidate the chosen destination, source selection, modal/visibility and tab. Closing, navigating or hiding the destination cannot retarget captured work. Folder rows still carry backend opaque refs, and Copy/Shift-Move flows through existing preview/conflict/progress/cancel/Journal/Restore.

## OS clipboard and mounted volumes

`system_clipboard` is a Main-only explicit-intent command. Windows uses standard file-drop clipboard data and a retained Main HWND; macOS uses native NSPasteboard file URL items with the action in the same item and checks changeCount around reads. File URLs preserve Unicode, punctuation and newlines without command/script interpolation. No arbitrary clipboard text, renderer path export, shell interpolation or background clipboard polling is allowed. Copy/Cut validates existing Transfer ticket identities. Paste reuses matching still-owned tickets (including their original identity); external files reuse the existing capture/Preview/execute path and its 256-path bound. Internal 1,000-item ticket admission stays unchanged. UI clipboard handoffs are ordered across panes, while actual file tasks remain on TransferOrchestrator. Late target changes release imported tickets without consuming a shared clipboard owner's tickets.

The mounted-volume list lives inside Files navigation, with one read-only foreground discovery request across subscribed panes, five-second refresh while that navigation is visible and focus/manual refresh. Unsubscription stops polling. It uses the existing known-locations projection, does not index or read file contents, and does not auto-open a newly attached device. BrowseService stores a non-serialized physical root binding at admission; Copy/Move folder refs and destination session/path refs recheck that root. This detects a replaced mount path without treating ordinary child-directory changes as a replaced root. Existing permission, read-only, disk-full, mutation identity, task cancellation, Journal and Restore owners remain responsible for operations.

Hosted source/fixture checks are not USB/SD or installed GUI acceptance. Explorer/Finder roundtrip, real removable media, safe eject and cloud/SMB availability/hydration qualification remain UNVERIFIED under #487/#553. No Beta/Release claim is implied. #552 copy paths and phase instrumentation remain unchanged; future measurements should distinguish clipboard/admission metadata traversal from preview hashing, durable copy/sync and publication rather than removing required identity/sync/journal work.

## Removable-media state and safe removal

The existing known-locations projection adds optional volume identity, source kind, read-only state, user-available/total bytes and safe-removal capability. Unknown metadata stays unknown. Windows lists logical-drive roots; macOS lists `/Volumes`. Both remain bounded and metadata-only. Discovery runs off the UI executor, shares foreground polling across panes, retains up to 32 disconnected entries and replaces observations on reconnect. Neither discovery nor reconnect admits an index/AI source.

`file_workspace_eject_volume` is Main-only. Its request accepts a discovered location ID and the displayed physical volume-root identity, never a renderer-selected device path. It re-resolves the current mount, rejects a replacement, acquires the existing operation run guard, and releases only Fylura-owned Browse enumeration, Preview and watch handles on that volume while preserving session roots/history. Windows resolves the mounted volume's storage-device number to its disk devnode and uses `CM_Request_Device_EjectW`; ejectable fixed USB SSDs are not excluded merely because their drive type is fixed. macOS uses NSWorkspace with a file-reference URL. System-volume and unadvertised removal are not offered. OS permission/busy veto is preserved; there is no force-dismount fallback or automatic retry. External applications/background work may still veto removal.

After a removal request, affected pane surfaces and discovery refresh, including after a veto. Older discovery requests cannot overwrite the post-removal refresh. The existing session root binding refuses disconnected/replaced media; reconnect to the original object can re-enumerate through the retained root. Disconnect never becomes bulk deletion or a new recovery ledger. Safe removal itself is an OS lifecycle operation, not a pretend restorable file mutation.

Destination preflight rejects observed read-only volumes. Windows regular-file Copy and cross-volume Move accumulate known streaming byte requirements against user-available space before content preview; directory allocation/metadata, races and quota changes remain OS-write checks. Logical-size capacity rejection is not applied to macOS clone/sparse transfers. Actual write errors still flow through existing staging cleanup, cancellation, durable outcomes and History/Restore; full/read-only feedback is localized. No guarantee that a preflight reserves free space is implied.

Focused checks cover removal identity/capability rejection, read-only/space decisions, own-reader release with session re-enumeration after veto, shared polling/removal ordering and live unplug/reconnect projections. Chromium fixture checks cover capacity/read-only display, busy refusal, identity-bound request and disconnected/reconnected state at desktop/narrow sizes. Target adapter compilation is not real USB/SD or installed GUI evidence: those remain **UNVERIFIED** in #487.

### Connected-storage copy profiling (#553)

The existing Windows native copy profile (`ZC_WINDOWS_NATIVE_COPY_PROFILE=1`) and macOS full copy profile (`ZC_MACOS_NATIVE_FULL_PROFILE=1`) accept an optional existing absolute `ZC_NATIVE_COPY_TARGET_ROOT` and mandatory `ZC_NATIVE_COPY_TARGET_KIND` (`usb_flash`, `mobile_ssd`, `mobile_hdd`, `sd_card`, `smb`, `cloud_client`, `local`). Each run creates an exclusive generated child, compares both variants against that same target, records observed source/target volume IDs and the operator's label, and cleans up only while the generated root retains its identity. Unplug/replacement leaves cleanup pending. Defaults and CI requirements remain unchanged. Do not point to an untrusted mount or assume the label proves hardware identity.

Windows retains #552's paired 1-GiB flush and 100k directory validation comparisons and Robocopy baseline. macOS retains sparse-clone and 100k streaming/clone phases, and adds a same-run 5k streaming comparison of the historical duplicate metadata write against the optimized path. Metadata application/verification, content hashes, sync, Journal and Restore remain required. The 100k fixture requires hardlink preservation; filesystems without it must report unsupported/failure rather than silently discard topology. The 5k regular-file comparison remains separately reported.

Cache state is uncontrolled and the added metadata pair has one run per variant in fixed order; report timings as diagnostic observations, not p50/p95 or a device-wide speed claim. Run repeated cold/warm cases on controlled hardware before qualification. Cloud results establish only local client-directory work, not remote upload completion. Real USB/SSD/HDD/SD, SMB and cloud-client performance remains UNVERIFIED when those targets are unavailable.

Diagnostic baseline before this optimization: [#560 macOS native CI](https://github.com/ArdenZC/Fylura/actions/runs/42738458491/job/129573589770) reported 100k streaming total 292,432 ms, directory copy/traversal 140,265 ms, source verification 35,796 ms, staging verification 32,345 ms and published-target hash 25,848 ms. Clone total was 221,871 ms with 99,999 clone successes. These are one hosted local-filesystem run, not removable/network/cloud measurements or a speedup claim. The redundant metadata application was identified in the traversal path; required hash work remains intact.
