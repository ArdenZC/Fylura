## Source-proven reasons an in-place PK migration is unsafe

1. `schema.rs:65-74` declares `files(id TEXT PRIMARY KEY, path TEXT NOT NULL UNIQUE)`; production scanner's `scan.rs:2861-3034` performs `INSERT ... ON CONFLICT(id) DO UPDATE path,name,mtime,size,...,is_stale=0` **before** root scan completion. Same path/file replacement can overwrite a published name, observation or annotation relation.
2. `scan.rs:1475-1606` has run/root/session ownership validation; `:1609-1691` still does direct global `UPDATE files.is_stale=1` and derived invalidation on root-path/seen assumptions. Root overlap can be misrepresented by a single global stale bit; the older E0 attributes are not frozen by a mere membership pointer.
3. `files.rs:411-437,605-630` restore operations UPDATE `files.id` and path; `:2351-2362` can DELETE an old row. `file_user_tags` `schema.rs:1911-1921` is FK `REFERENCES files(id) ON UPDATE CASCADE ON DELETE CASCADE`. Blind deletion loses user tags; blind PK update can carry tags to the wrong physical incarnation.
4. Other product FKs referencing `files(id)`: `file_fingerprints` `schema.rs:1217-1249`; `duplicate_group_members` `:1299-1312`; `content_run_items` `:2263-2268`; `content_artifacts` `:2296-2299`. `organization_plan_items.file_id_snapshot` `:1989-2026` records a historical ID without live FK; operation/cleanup logs also carry path and platform identity. **All** need correct lineage/actionability, not a bulk rewrite.
5. `scan.rs:2923-2976` captures `fs_safety::capture_physical_identity`, storing a **filesystem observation hash** including path, size, mtime, ctime and physical identity where available. This is valuable provenance but **not a durable UID nor always present**. Windows/macOS resource moves, inode reuse, hardlinks, network drives, and unavailable identity need differentiated policies. A hash changing on mtime is not evidence of a new physical incarnation by itself.
6. `library/mod.rs:727-849` queries list and count in one main SQLite transaction and `:557-591` stores `library_query_state.revision`/cursor snapshot; `library/tags.rs:107-175` mutates current tags in a transaction by selection of `files.id`. The new projection/FTS slot version must be pinned **before** reader SQL and must cause safe cursor/revision expiration; a reader cannot independently mix an E1 query from E0 tags/metadata.
7. `schema.rs:2763-2818` current external-content trigram `files_fts` indexes physical `files`, and `files_au` triggers on **all UPDATEs**, even if only `is_stale` changed. The F1 index file must own separate immutable per-epoch name/path projection. Do not claim WHERE EXISTS, filter-after-LIMIT or merely changing the FTS trigger gives exact effective-visible BM25.

## Proposed identity and authority domains (logical records, not approved SQL DDL)

**I1 LegacyRows (compatibility only).** Keep `files` and all old path-ID/FK relationships intact during expansion and dual-read; allow existing operation journals to finish. An old `files.id` is a *legacy display/history key*, not a proven physical identity. Never delete or rewrite it as migration cleanup. Apply an explicit dual-write fence only after enumerating owners; until then **new authority must not be made actionable**.

**I2 SourceIncarnation.** Immutable `source_uid` (opaque random/stable minted lineage ID, not derived from path) plus `origin_observation`, physical object claim and verification class `VERIFIED / UNVERIFIED / CONFLICTED / RETIRED`; separate `source_rev` CAS and history. Physical object key may match across rename or hardlink aliases when OS proof supports it, but link/path claims are distinct, versioned. Same path with **different proven object** => **new source_uid**; same object with updated content metadata => new observation revision under same UID, with derived validity revocation. Weak/unavailable identity => keep historical facts, block irreversible cross-incarnation attachment/actions, enter reconciliation. Never equate size/mtime, path or a hash alone with identity proof.

**I3 ImmutableObservation.** `(source_uid, observation_rev)` carries the frozen indexed `path,name,extension,size,mtime,ctime,is_dir`, observation/physical proof digest, classification-action eligibility revision and provenance. New scans stage rows under a run owner, never UPDATE published E0 observation text. A candidate may reuse a still-valid previous observation, but no in-place text mutation. Source action identity is separately checked at *execution*, not assumed from old historical observation.

**I4 RootEpochClaim.** `(root_id, root_epoch, source_uid, observation_rev, path_alias)` immutable after seal; normalize and check enabled root ID, permissions, exclusions and watcher coverage. Root A's missing file can retire only A's claim; root B's valid published claim preserves its global visibility. An overlapping-root UNION must deduplicate logical source/alias policy deterministically and provide one selected frozen FTS document. Root disabled/permission-degraded is distinct from file disappearance; old published readable-but-degraded views may remain only when no live safety revocation is known.

**I5 LibraryPublicationAuthority.** One durable *global* `catalog_epoch` and `fts_slot_id` plus `root_revision_vector_digest, source_writer_watermark, watcher_proof, indexed_corpus_digest, library_query_revision`. Reader obtains this coherent tuple on its main-DB snapshot, validates availability of the sealed slot, pins it, then reads from that exact slot. Published FTS corpus = global effective-only source documents; a selected-root filter applies before pagination, not before global corpus scoring. Preserve stable rank ties/mtime/name/UID as tested; do not change query semantics by default.

**I6 UserOwnedFacts and lineage adjudication.** Preserve legacy `file_user_tags`, tag definitions, notes, user-corrected classifications, operation/cleanup journals and history as-is while introducing a **separate non-destructive attribution ledger** `(legacy_file_id, legacy_revision, candidate_source_uid?, claim_class, evidence, human_decision, updated_rev)`. New UID-bound user facts become active **only** if `VERIFIED` by durable physical lineage or a **recorded explicit user decision**. Existing tag relation with no defensible physical proof => `UNRESOLVED`, retain legacy fact and surface it for review; never attach it to an arbitrary new file at the same path. If verification contradicts multiple competing claims => `CONFLICTED`, preserve all historical facts but deny current action. Any tag change executed after cutover targets a pinned UID+rev inside the current authority transaction; an old-path-selection token cannot grant write rights.

**I7 DerivedValidity.** Content, duplicate fingerprints/groups, AI classifications, plan previews and indexing/checkpoint results are historical facts keyed by old IDs until migrated; current actionable projection must prove matching `source_uid, observation_rev, root_epoch, user/policy/worker_rev` and execution-time physical identity. Old derived result remains visible as history but cannot be applied to a new incarnation; deferred bulk invalidation/GC is bounded and restartable.

### Explicit invariants

- **V01** no user fact lost or transferred by old `files.id` rename/delete/path reuse; legacy FKs remain valid during migration.
- **V02** E0 Reader retains frozen E0 name/path/mtime and matching effective-only FTS rank after E1 staging, including fresh E0 readers until authority switches.
- **V03** a root-level stale claim cannot remove a valid overlapping published root claim; no duplicate FTS doc from overlapping aliases.
- **V04** Writer CAS checks `source_uid/rev + root/run/session/Watcher rev + current writer authority`; a stale or ABA write never mutates a newer published source.
- **V05** publication transaction touches a constant number of authority rows/revisions (or bounded O(changed roots)), never 100k `UPDATE files`, external-content FTS rebuild or full filesystem walk under one writer lock.
- **V06** the published FTS slot corpus, immutable row projection, list/count/tag selection/cursors, derived validity and rank authority all refer to the same `catalog_epoch`.
- **V07** identity/permission revocation blocks irreversible actions immediately; old known-safe metadata can be labelled degraded/read-only only under a proven safe policy.
- **V08** shadow slot build/backup/rename/cancel/GC and SQLite authority/metadata snapshots are crash recoverable without ghost READY, user data loss or unsafe fallback.
- **V09** no cross-process writer, legacy direct SQL mutation, operation restore, scheduler job or user-tag writer can bypass the switch-over gate.
- **V10** no policy change to independent Global Index #380, explicit File Workspace, Storage Analyzer or Index Scope scope/exclusions without separate authorization.

## Migration and cutover decision (not executable migration SQL)

**M0 Freeze and audit.** From Schema37, require read-only backup and representative per-table counts; `PRAGMA foreign_key_check`, `integrity_check`, FTS integrity, `files.path`/legacy-ID uniqueness and tag/fingerprint/content/history retention baselines. Check `ensure_*` migrator paths and every affected FK writer. Refuse incomplete/unreadable OS identity as verified lineage.

**M1 Expand-only, no activated reads/writes.** Introduce *separately version-gated* identity/observation/root-membership/projection/authority/attribution structures, indexes and test-only migration verification **without changing current `files` IDs/FKs or mutating user facts**. Version number/DDL is subject to separate Owner schema allocation and coordination with #380; this document explicitly does not allocate v38. On migration failure rollback transaction; avoid large 100k FTS copy in the schema-upgrade writer transaction.

**M2 Reconstruct and classify.** Bounded idempotent backfill from legacy `files` into observation candidates, capturing *actual* OS physical proof when feasible; store provenance and `VERIFIED/UNRESOLVED/CONFLICTED` counts. Retain every unverified tag/annotation and history row as unbound legacy facts. Build root claims from known run/Watcher + independent root verification; a simple historical path prefix is **insufficient** to certify coverage. Repeated resumable batches; current production remains authoritative throughout.

**M3 Shadow prepare and seal.** Build a full globally effective-visible F1 SQLite slot with exactly frozen projected text, immutable generations, FTS5 trigram BM25, position/cursor semantics; prove root union/overlap, old E0 and new E1 independently. F1 full source build O(N), each root-delta copies O(slot DB bytes); preserve explicit disk-space/copy/memory estimates and cancellation. Stage metadata/FTS slot outside main writer transaction. Seal checksum, index stats, root/run/writer/Watcher revisions and `PRAGMA integrity_check` before publish; never publish an unverified slot.

**M4 Dual-read/dual-write guarded qualification.** Before authoritative switch, run shadow queries against **the same persisted snapshot and approved UID mapping**, compare list/count/selection/tags/FTS float bits/page/cursor; never use a divergence to mutate a user fact. Activate a durable provenance/write barrier for all scanner, Watcher, file ops/restore, tag, content/dedupe/AI, direct file SQL writers, validated by a source-local callpath ledger; if *any* uncovered writer exists, **NO CUTOVER**. Explicit Browse/Global Index remain outside. No unbounded continual full dual-FTS rebuild as a hidden default.

**M5 Short atomic authority switch.** Only after M0-M4 gates pass, confirm ownership, sealed slot existence/digest and source/root/watcher/metadata revisions in a short `BEGIN IMMEDIATE`, update `catalog_epoch + slot + library_query_revision + read-mode` atomically, commit. **No cross-database atomic commit is claimed:** slot must be fully durably staged *before* pointer transaction. If slot and pointer disagree after restart, fail closed / reconcile; never silently promote an unsealed slot.

**M6 Hold-old / recovery / bounded cleanup.** Retain old slot, legacy rows and user-owned facts until all readers/jobs/old snapshots have expired under a reliable monotonic lease; separately fence direct action requests. Reconcile interrupted `pre-stage / sealed-before-commit / commit-before-ack / slot-unavailable / interrupted-delete / GC` states. Test actual Windows open-handle semantics and macOS permissions/rename; asynchronous unlinks only after reader liveness proof, never in main writer transaction. Roll back **active pointer** only to a provably intact previous slot with an explicit revision CAS; do not restore stale source/Watcher/user writes or erase newer owners. Never silently reinstall old `is_stale` as product truth after final cutover.

**M7 Remove obsolete path authority — LATER separate Owner GO.** Do not drop/rename `files`, rewrite unique path constraint, delete old user facts, remove triggers, or retire legacy SELECT/restore paths in B4-01. Remove them only once all product code/protocol and rollback evidence is complete.

## Cross-file durability is the decisive unresolved condition

The F1 separate-slot SQLite file and the main authority DB do not participate in a single SQLite ACID transaction. Correct ordering *may* be: (1) write and integrity-check a private slot, (2) sync/fsync the slot and containing directory as OS permits, (3) seal durable manifest + digest and verify the file, (4) commit main SQLite pointer under CAS, (5) allow readers to pin, (6) retire old after durable reference expiry. **This ordering is a proposed proof obligation, not a verified platform protocol.** Disk-full, power interruption between fsync/rename and commit, Windows file-sharing delete/rename and backup/restore (both data DB and index-slot set) must be tested. Incomplete slot => old authority; pointer to missing/corrupt slot => READ_ONLY_RECONCILIATION / no destructive action, never false READY. If these cannot be bounded/verified, B4 is blocked until a safer product-linked storage choice is selected.
