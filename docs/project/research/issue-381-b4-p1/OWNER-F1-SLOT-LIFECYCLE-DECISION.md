## 1. Owner decision in one paragraph

**Choose F1 (a sealed, immutable, effective-visible-only SQLite FTS5 trigram slot per catalog epoch) as the preferred architecture, subject to separate integration proof.** Reject F0 (physical-all-files BM25 plus post-filter) as semantically wrong and F2 (mutable physical FTS + derived effective statistics) as insufficient for fresh E0 readers after text updates. **P1 must be separated into P1A test-only durability/reader-pin design-and-qualification, then a separately authorized P1B dormant product adapter.** Neither may activate `library_generation_authority.read_mode='generation'`, change the current `files_fts`/reader/cursor, backfill user metadata or claim that the new FTS already represents genuine root coverage. P1A can use an independently labelled frozen corpus Oracle; full production effective membership requires separately proved SourceUID/RootEpoch ownership in P2.

## 2. Current source boundary, not inferred future behavior

1. `src-tauri/src/db/schema.rs:7,10-152,181-208,908-1003`: Schema38 contains exactly four P0 dormant tables `library_source_incarnations`, `library_source_observations`, `library_legacy_attributions`, `library_generation_authority` plus four indexes. Its default singleton is `legacy,0,NULL,revision1`. The actual fast-open `validate_library_identity_schema()` **requires that exact legacy sentinel**, so any P1 experiment writing a generation pointer to it causes a subsequent `Database::open` refusal. No such write is permitted.
2. `src-tauri/src/db/connection.rs:56-118, configure_connection`: main SQLite uses `r2d2` max pool **8**, journal WAL, `synchronous=NORMAL`, `mmap_size=3_000_000_000`, foreign keys ON and **5,000ms** busy timeout. The isolated #399 probe used `synchronous=FULL`; **that is not evidence main product durability is FULL**. A correct multi-file protocol cannot assume a unified SQLite ACID boundary.
3. `src-tauri/src/db/queries/library/mod.rs:559-576,727-864,1388-1455,1898-1975`: Library V2 opens a main DB read transaction, binds `library_query_state.revision` to cursor/count and reads `files` joined with `files_fts`; rank comes from `bm25(files_fts,6.0,1.5)`. Native enrichment is deliberately outside the pooled SQLite lease. Neither slot epoch, physical source UID nor reader pin is in the existing production request/response contract.
4. `src-tauri/src/db/schema.rs:3047-3110`: legacy `files_fts` is an external-content trigram FTS5 table indexed on physical `files`; its `files_au` trigger runs on ANY UPDATE. P1 may not replace this trigger or FTS corpus.
5. `src-tauri/src/db/queries/scan.rs:1475-1598,1609-1691`: `persist_scan_batch` writes live `files` in a main DB transaction; `reconcile_missing` can directly set global `files.is_stale=1`. Existing root overlap/source authority is **not** sufficient to certify an immutable effective-visible slot.
6. #399's actual product-bundled SQLite 3.51.3 / FTS5 trigram research showed F1 feasible in a reduced Linux model with native rank parity; its 100k initial build ~3,865ms, prior-slot copy+delta ~935ms, publication pointer writer ~0.72ms, and high-hit query ~386ms are **single samples only**, not Windows/macOS/native app budgets. The probe's `leases`, logical `lease_clock`, and SIGKILL tests are not shipped product semantics.

## 3. Authority separation / non-negotiable records

Maintain distinct domains:
- **Main source truth:** present legacy `files`/user facts and dormant P0 `source_uid` containers. Do not use `files.path`, mtime/size or filesystem-observation hash as sufficient identity proof. Generation publication cannot be actionable before P2 full writer arbitration.
- **Candidate source snapshot:** immutable, versioned `(source_uid, observation_revision, frozen_name/path/size/mtime, root-claim/proof)` originating from a *qualified* source/root epoch. For P1A only, synthetic labelled inputs; for future product, **no fabricated TRUE root health** from `scan_seen` or prefix matching.
- **Private slot:** one SQLite index file per immutable version/candidate with **globally effective-visible** documents only, deduplicated across overlapping root claims, frozen indexed name/path and stable UID/observation mapping. It must preserve the exact production trigram query language/weights and stable tie ordering. Selected-root filter occurs before page slicing, but BM25 document statistics are global effective-visible, not per-root.
- **Durable slot registry / manifest:** a future Owner-approved record (e.g. slot ID, layout version, source snapshot revision/digest, root vector, writer watermark, candidate epoch, expected count, content digest, file byte digest, sealed timestamp, state). **Schema38 has no registry or reader-lease table**: a new schema migration requires independent cross-track Owner version arbitration. Do not infer or auto-allocate Schema39 here. File-system-only JSON manifest is insufficient by itself to provide atomic cross-process claim/GC fencing.
- **Reader pin / retirement state:** distinct persisted generation reference and liveness protocol. P1A demonstrates a test-only pin, while actual product must prove crash-tolerant cross-process registration, expiration, no reader resurrection, no unreferenced slot unlink and bounded 8-connection pool impact. No wall-clock-only expiration claim; restart, sleep/wake, PID reuse, clock rollback and ABA must be tested. File-handle ownership is a safety layer, **not a substitute for durable publication authority**.

**Generation pointer invariant:** until fully separately approved, P0 `library_generation_authority` remains exactly `('legacy',0,NULL,1)`. Future product publication requires a separately versioned validator and a coherent reader/cursor/count/tag-selection contract; setting `read_mode='generation'` alone is prohibited.

## 4. Proposed lifetime state machine (design, not deployed DDL)

`ABSENT -> PREPARING -> SEALED_UNPUBLISHED -> [future, separately approved P2/P3: PUBLISHED] -> RETIRING -> GC_ELIGIBLE -> REMOVED`.

- **PREPARING:** create slot in private app-managed data directory with randomized non-guessable name. Never under the user's indexed roots, caches subject to OS cleanup, application install directory, or a directory synced/evicted by an uncontrolled cloud provider. Enforce filesystem permissions and redaction of indexed paths in logs; index is a sensitive unencrypted copy of user filenames/paths unless an independent encryption design is approved. No external caller may treat preparing slot as READY.
- **SEALED_UNPUBLISHED:** writer finishes all FTS/content transactions and performs a bounded checkpoint/close so the immutable slot is a single validated canonical SQLite artifact (or explicitly versioned complete file set). Verify `PRAGMA integrity_check`, FTS5 integrity, exact UID/observation/row mapping, source and global-visible rank parity; compute source-provenance and SHA-256 **of final sealed bytes**. Sync file and parent directory with OS-specific proof where available. Write seal manifest to its own durable temp/commit protocol. Reopen READ ONLY and validate digest after close. Failure => QUARANTINED/UNAVAILABLE, never create a false published pointer. Do not take `immutable=1` on a file that may still be mutated by another connection.
- **PUBLICATION (out of P1):** only after P2 source/root writer CAS and P3 cross-file/OS qualification, a short main-DB conditional transaction may change epoch+slot+query revision together after confirming a sealed slot; never run O(100k) FTS rebuild, SQLite online backup or filesystem walk under the main writer transaction. Since the main DB and private file have **no joint ACID**, a publication barrier must verify source revisions, manifest availability and durable seal *before* commit, and runtime verify slot again when opening. P1 adds **zero** production publication path.
- **READER PIN (P1A harness / future contract):** snapshot coherent epoch+slot+query/root/source/user revisions; register an irrevocable/expiring claim with a GC serialization barrier **before** releasing the authority snapshot, then open exactly that slot and force a real SQLite read transaction before claiming a usable snapshot. If pin registration or open fails, abandon/release claim and return explicit error or old **still-current, separately validated** authority; never silently fall back to mutable `files_fts`. Main DB source metadata/query and private slot must be bound to the same published epoch. Reader registered after GC's retire transition must be rejected.
- **Avoid pin/GC TOCTOU:** opening a slot and adding a lease as independent unlocked operations is unsafe; GC can delete between them. The #399 test harness uses `BEGIN IMMEDIATE` around a pin insert **for every reader**, which is acceptable research but not authorized for production without showing it does not regress latency, pool availability or 5s SQLite writer liveness under real concurrent load. Alternative nonblocking/proxied registration is open to evaluation, but MUST furnish equivalent cross-process serialization proof.
- **RETIRE & GC:** retire only a proven noncurrent slot and block new pins with a durable CAS; wait for *all* live/recoverable leases and actual OS file handles to clear, then stage tombstone/delete **outside** main DB writer transaction. On Windows, deletion can fail under open handles, so defer/retry idempotently with bounded work; on macOS/APFS exercise directory durability and rename recovery. Never unlink user files, the main DB, original `files_fts`, manifests/slots still referenced by a backup, or old user-owned metadata. Maintain explicit disk-budget/backpressure and avoid retry storms.

## 5. Failure and recovery decision table

| Event / barrier | Required future response (P1A should model) |
| --- | --- |
| Crash before first slot write, partial build, FTS corruption | Candidate quarantined; no active authority change; no user facts changed |
| Crash after SQLite final close before manifest seal | Orphan candidate; verify/reconcile or quarantine, never infer SEALED from existence |
| Crash after manifest seal before future main pointer commit | Sealed unused slot safe to retain for reconciliation; never auto-publish |
| Future crash during pointer CAS/commit | On restart read committed main authority and verify immutable slot/digest; no mixed old/new exposure |
| Pointer refers to absent, altered or unsealed slot | `READ_ONLY_RECONCILIATION`; no destructive operations, false READY or silent legacy fallback |
| Bad/expired/replayed cursor, lost reader pin | Explicit `snapshot_expired`/revoked; old E0 query cannot load E1 text or recycled slot |
| Disk full during copy/build/sync | Bound temporary storage and reject candidate, keep legacy and existing sealed slots intact |
| Concurrent tag/operation/source writer advances watermark | Reject stale candidate/publish CAS; do not overwrite user facts |
| Windows file sharing violation / open handle | No forced delete; record blocked GC and retry later outside writer lock |
| macOS crash/power loss during rename/fsync | Re-open integrity and durable manifest proof; claims remain conditional pending native validation |
| Broken backup set: main DB without active slot or vice versa | No restored actionable generation; verified recovery or read-only reconciliation only |

**Important:** a Linux `SIGKILL` test does NOT establish sudden power-loss durability, SQLite checkpoint completeness on Windows, NTFS handle safety or APFS directory sync guarantees. Do not claim solved if not directly measured.

## 6. Interfaces frozen now vs later

**Frozen P1A (test-only):** `SlotBuildInput` synthetic frozen UID/observation docs + root memberships and digests; `SealedSlot` digest/manifest; `TestPin` epoch/handle/revocable lease; `RecoverSlot` state/result; `GcDecision` reason. All inside isolated test/fixture code; no production main DB schema or automatic app service.

**Reserved future P1B (not yet authorized):** private slot builder/stager/verifier/read-only resolver plus product-accurate pooled connection hooks; any main-DB registry/lease needs explicit SQL/schema number, timeout plan, profile and migration atomicity review. Adapter exposes only `prepare`, `verify`, `open_shadow`, `retire_candidate` and never `activate`. No async periodic scan or initialization indexing default. How P1B obtains a **valid** corpus from P2 remains a documented dependency; the adapter must refuse unknown source/coverage instead of opportunistically querying mutable legacy rows.

**P2 dependency:** independently approved SourceUID identity verification, root epoch claims, writer CAS and family of callsites in #400's source/FK matrix; immutable effective projection must be available before a product shadow search is considered proof.

**P3 dependency:** Windows/macOS native file-handle, crash/recovery, power-loss, long reader, disk-space, and 100k writer/reader qualification before any real user generation cutover.
