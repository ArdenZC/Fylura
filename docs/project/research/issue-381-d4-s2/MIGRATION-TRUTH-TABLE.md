# Schema 37 → candidate source mapping truth table

This is a candidate mapping only. No schema version is allocated. `files.id` is the Schema 37 storage/FK key; in current Scanner rows it is usually the path. New source identity must use an opaque `source_id` and an opaque new `files.id`.

| Input row or event | `files` row | `file_sources` | Path/generation relation | Old side data | New same-path source |
|---|---|---|---|---|---|
| Existing Schema 37 live row, identity unknown | Preserve the row and `rowid`; preserve `files.id` exactly even if it equals path. Rebuild only removes `UNIQUE(path)`. | Add new opaque `source_id`, map it to the old `files.id`, status `legacy_unverified`. | Add a legacy path snapshot with `legacy_unverified`; no root member or current manifest path. | Keep each FK value unchanged. Preserve non-FK snapshots unchanged. | Not created by migration. |
| Existing Schema 37 stale row | Preserve row, `is_stale`, rowid, and content fields as historical evidence. | Same legacy mapping; never infer identity from stale bit. | Legacy snapshot only. | Keep tags, fingerprints, groups, content, findings, and operation history. | A later observed file receives a new source unless explicitly claimed by a user and native observation. |
| Owner explicitly claims a legacy record for a selected observed file | Keep old payload row and FK anchor. | Keep the old selected source ID, advance `source_revision`, record actor, authorization digest, and claim kind. | Append a verified path entry and bind it in a complete root generation. Do not rewrite the unverified snapshot. | Existing state remains attached to this explicitly claimed source. | The source is the chosen legacy record only because of the explicit claim. |
| New, different identity takes a deleted file's path | Keep old row at the same path value; same-path duplication is allowed. Insert a new row with opaque `files.id` and no transferred metadata. | Old source stays retained and loses effective membership. Insert a new `source_id` mapped to the new file row. | Old generations remain history; a complete new generation adds new source/path entry; manifest projection selects only new source. | Old FKs and history remain on old `files.id`. | New source gets no automatic tags, notes, classification, fingerprint, duplicate membership, content, findings, or Global Index AI state. |
| Verified rename/move of same directory entry | Keep the same `files.id`; update only current name/path snapshot in the publication transaction. | Keep same `source_id`; increment source/path revision. | Append a new `path_entry_id` linked to same source and verified physical epoch. Root generation changes membership path entry. | Side rows remain on same `files.id`. Prior path entry and operation history remain. | No new source is made for a verified same-entry rename. |
| Cross-volume move or copy/delete with no continuity proof | Preserve former row as old source. | Allocate new source ID for the new observation. | Create new path-entry and root membership. | No automatic side-state transfer. | New source, even if bytes/hash match. Explicit user data copy remains a separate audited operation. |
| Hard-link alias added | One new retained `files` row for the alias path. | New source ID; do not merge with existing alias source. | New path-entry; same physical-identity epoch only when both live native handles prove aliasing. | Tags and notes stay specific to each source. | Dedupe may relate aliases; identity and user data stay separate. |
| Same source/path observed by overlapping roots | One `files` row and one source. | No duplicate source crosswalk. | Root generations both reference the same source/path-entry. One manifest projection row. | Single association set, not duplicated per root. | None. |
| One of two owning roots removes its membership | No `files` row is deleted or rewritten. | Source unchanged. | New manifest drops only that root head/membership; other root head still includes source. | All associations remain. | No new source. |
| Last effective root removes membership | No `files` row is deleted. | Source row remains retained. | New manifest has no effective membership/path projection for source. | All associations remain; active counts/search/actions hide them. | A later same-path file creates a new source. |
| Two roots assert different source identities at the same path | Both source rows and evidence remain. | No source merge. | Projection uniqueness conflict rejects candidate manifest before pointer CAS. | No transfer or cascade. | Reconciliation required. |
| One source has two distinct path entries in the proposed effective manifest | Source row remains. | No duplicate source ID. | `(manifest_id, source_id)` uniqueness rejects two-current-path projection; reconcile all affected roots together or keep prior manifest. | Unchanged. | No arbitrary “latest path” winner. |
| Migration exception or process interruption before commit | Original table and unique path constraint return; original IDs, rowids, indexes, triggers, child rows remain. | No crosswalk is published. | No active manifest changes. | Unchanged. | Retry migration after startup recovery. |
| Migration transaction committed, response lost, process restarts | Rebuilt table and marker both exist. | Existing crosswalk retained exactly once. | No root ownership is auto-created. | Unchanged. | No duplicated transfer. Startup validates, then resumes with new binary generation. |
| Explicit retention-approved GC | Delete is blocked absent a durable authorization and absence of references/pins. | Delete only after references and retention policy permit. | GC first proves no active/pinned manifest, path entry, generation, job, cursor, or reader lease depends on it. | Cascades are allowed only if product retention policy explicitly says these rows may expire. | Never used for path reuse or stale publication. |

## Historical relationship inventory in the Schema 37 Harness

The fixture populated one row per relation and compared counts before/after migration:

| Data | Schema 37 relation/key | Expected candidate behavior |
|---|---|---|
| Tags | `file_user_tags.file_id → files.id` with `ON UPDATE/DELETE CASCADE` | Old tag stays on old file FK. New source has zero tags. |
| Fingerprint | `file_fingerprints.file_id → files.id` | Old identity/hash row stays on old file FK; never copied to same path. |
| Duplicate evidence | `duplicate_group_members.file_id → files.id`, group references `dedupe_runs` | Old group/member remains retained; active visibility derives from manifest. |
| Content | `content_artifacts.file_id → files.id`; separate `content_artifact_fts` row | Artifact and raw FTS hit remain stored; effective query hides them after membership removal. |
| Content run history | `content_run_items.file_id → files.id` | Existing FK remains valid; no cascade occurs because source row remains. |
| Classification and user feedback | `classification_history.file_id` / `classification_feedback.file_id` without FK | Snapshot stays byte-for-byte owned by old ID; no path-based reassociation. |
| Analysis/finding evidence | `analysis_findings.primary_subject_id`, `analysis_finding_evidence.subject_id` path snapshots | Historical finding/evidence remain; active-result lookup requires a future explicit source binding. |
| File operation history | `operation_logs` stores before/after paths and identity snapshots without file FK | Retain as operation history; path equality is not current source identity. |
| Global Index AI result | `ai_analysis_state.global_entry_id → global_entries.id` | Global row and AI payload remain independent; no new managed-source bridge is inferred from matching path. |

The full set of five direct foreign-key tables was also enumerated from the captured Schema 37 DDL in the Harness output. Other relations that embed `file_id` text or paths without FKs require source audit and explicit read semantics before production work.
