# Issue #474 — FTS search contract alternatives (P0 decision study, NOT production)

Scope: read-only / test-only from \`master\` after #488. Existing 1M Windows Release FTS p95 **331.420 ms report**, **346.993 ms invoice** against an unchanged 100ms target. Exact 512+1 rank-frontier at #490 cannot prove top-80 due to large BM25 boundary ties; the older joined rank stream regresses 100k. Do not repeat those attempts.

## Alternative A — keep current semantics, add exact query-result cache
Preserve the current five-tier priority, FTS5 weighted BM25 \`(8,2,1)\`, tie keys \`modified_at_fs DESC, id ASC\`, visibility before LIMIT, full 4096 candidate window and Snapshot consistency. A cache can avoid repeat recomputation for hot *identical* queries but does not reduce first/miss latency at 1M. Cache keys need normalized full term + candidate window + source/index generation and relevant volume/scopes/managed-state versions. Invalidations include index entry INSERT/DELETE, name/path/extension/FTS text changes, mtime edits (tie order), stale state, volume enable toggles, managed scope/entry flags, and schema migrations. WAL writer/reader races must be snapshot consistent; a loose \`PRAGMA data_version\` alone is not accepted. Measure bounded memory, disk persistence (if any), churn, write overhead and cold-hit performance before any rollout. **A cache cannot honestly close the 1M cold 100ms gate.**

## Alternative B — default fast recent-first search, exact BM25 as an explicit option
Search recent indexed global entries in \`modified_at_fs DESC, id ASC\` order and check simple ASCII normalized substrings. This exploits the existing \`idx_global_entries_modified_at\` and may stop after 80 relevant active rows, rather than score 50k FTS matches. It is a **different relevance contract**, not a SQL-equivalent replacement for weighted BM25. It may return different 80 IDs/order; Unicode folding, quoted phrases, cross-field matching, punctuation, trigram length and long text still require exact analysis or FTS fallback. The current five-tier search structure means this experiment concerns **only the last FTS tier**, not earlier exact/prefix precedence. If pursued, name the new product mode, retain explicit "Exact relevance" mode, and require UX signoff. No silent default switch.

An opt-in 100k Windows Release experiment \`mode=fts_recency_release\` (manual GitHub Actions workflow_dispatch) compares (i) exact production pooled results, (ii) full active-row membership for FTS5 MATCH vs recent-first substring on the same fixture, (iii) the first 80 overlap and order, (iv) 5 warmup + 30 samples of only the recency-driven SQL and its real EXPLAIN. All ID/order differences are emitted, not hidden. The original FTS index, FTS triggers, SQLite schema, index implementation, API, product ranking and 100ms gates **do not change**. The experiment is fixed at **100000 rows**; do not extrapolate or auto-run 1M.

## Alternative C — dedicated inverted index / Tantivy
Evaluate a separate index with custom collector and file/source generation boundaries, including Unicode/Chinese phrase behavior, weighting, ranking determinism and managed state. Tantivy's BM25 is **not guaranteed to numerically match SQLite FTS5 BM25**, nor to implement trigram phrase semantics without custom tokenizer and indexing; a drop-in migration is prohibited. Need dual-write/rebuild, CPU/RAM/disk/file-watcher costs, failure recovery, WAL→index consistency, cross-process service IPC contract, and Windows/macOS installation assessment. Do not claim performance without a project-corpus benchmark.

## Decision gates
First examine the scoped 100k Release experiment. If recent-first membership and latency are compelling but top80 order diverges, open a **product contract / UX decision** before changing production. If performance is not compelling, reject. Caching remains a warm-query quality improvement only, not a solution to the cold 100ms gate. Full 1M exact-BM25 equivalence may necessitate a new index/scoring architecture; do not lower the existing gate, remove BM25 silently or relax exact-result oracles.

Release remains NO-GO; owner #474 stays OPEN. No production feature, Schema migration, build release, automatic job/1M/Full Validation dispatch in this research PR.
